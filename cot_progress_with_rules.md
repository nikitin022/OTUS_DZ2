# CoT_PROCESS_WITH_RULES — применение Chain-of-Thought к разработке сайта (вариант «с правилами»)

> Документ фиксирует применение техники **Chain-of-Thought (CoT)** к решению
> сложной задачи разработки «Сайт услуг парикмахера и массажиста».
> Проект — **ДЗ2** курса OTUS «ИИ-агенты».
> В данной версии применялись **оба** свода правил: `hw_ai_rules.md`
> **и** `rules.md` (R1–R14) — отсюда название варианта **«с правилами»**
> (каталог `with_rules/`).
> Сравнение с вариантом **«без правил»** — см. отдельный файл
> [`comparison_with_vs_without_rules.md`](./comparison_with_vs_without_rules.md).

---

## 1. Выбранная сложная задача

> **Реализовать работающий статический сайт-визитку мастера** (парикмахер + массаж)
> со всеми разделами — услуги/прайс, галерея работ, форма записи, контакты —
> в полном соответствии с правилами проекта `hw_ai_rules.md` **и** `rules.md`
> (R1–R14), включая адаптивность и доступность (a11y, прогрессивное улучшение).

**Почему задача «сложная»:** объединяет несколько самостоятельных подзадач
(структура данных, семантическая разметка, стилизация с переменными, модульная
JS-логика с валидацией), требует соблюдения архитектуры и стандартов качества
(a11y, адаптив, progressive enhancement) — идеальный кандидат для декомпозиции CoT.

**Задача выбрана идентичной** варианту `without_rules`: только так корректно
сравнивать влияние наличия/отсутствия правил (см. файл сравнения).

---

## 2. Декомпозиция задачи на логические шаги (CoT)

Задача разбита на **5 последовательных шагов**. Каждый шаг — отдельный промпт
по методологии **RTCF** (Role → Task → Context → Format) с последующей проверкой
и conventional commit.

```
Шаг 1 (Архитектура и данные) ─▶ Шаг 2 (Разметка HTML) ─▶ Шаг 3 (Стили CSS)
        ─▶ Шаг 4 (Модульная JS-логика) ─▶ Шаг 5 (Тесты, проверка, документация)
```

| Шаг | Название | Файлы | Commit |
|-----|----------|-------|--------|
| 1 | Декомпозиция и схемы данных | (решения в этом документе) | — |
| 2 | Семантическая разметка | `with_rules/index.html` | `feat(html)` |
| 3 | Стилизация | `with_rules/css/main.css`, `with_rules/css/components.css` | `feat(css)` |
| 4 | Модульная JS-логика | `with_rules/js/main.js`, `js/utils.js`, `js/modules/*` | `feat(js)` |
| 5 | Тесты, проверка, документация | `with_rules/tests/booking.test.js`, этот файл, файл сравнения | `test(booking)`, `docs` |

## 3. Шаг 1 — Декомпозиция задачи и схема данных

### 3.1 Промпт (RTCF)

```text
R: Ты — технический архитектор/тимлид проекта «Сайт услуг мастера».
   Сначала прочитай hw_ai_rules.md и rules.md (R2) и строго им следуй.
T: Декомпозируй задачу «Реализовать главную страницу сайта» на подзадачи
   с критериями готовности, порядком и зависимостями.
C: Стек и структура — по hw_ai_rules.md (статический сайт file://,
   HTML5/CSS3/vanilla JS ES-модули; каталоги index.html,
   css/{main,components}.css, js/{main.js, modules/, utils.js},
   assets/images|fonts; БЭМ, 2 пробела, kebab-case/camelCase,
   а11y, progressive enhancement).
   Учти rules.md: R12 (структура файлов), R13 (модуль = предметная область),
   R11 (без фреймворков и недокументированных CDN), R10 (без секретов).
   Данные услуг/работ — JS-массивы.
F: Упорядоченный план подзадач (файлы → критерии приёмки → зависимости →
   тип commit), финальные схемы данных для услуг и галереи.
```

### 3.2 Результат

- Утверждён порядок исполнения: **1 → 2 → 3 → 4 → 5** (п. 2).
- Каждый модуль — одна предметная область (услуги, галерея, запись, контакты) — **R13**.
- **Схема услуги:** `{ id, name, category, price, duration, alt }`
  (цена в рублях — целое число, длительность в минутах).
- **Схема работы галереи:** `{ src, alt, caption }`.
- Данные вынесены в JS-модули (`services.js`, `gallery.js`) — единый источник
  для рендера карточек и наполнения формы записи.
- План коммитов на ветке `feature/site-with-rules` (**R14**: ветка на задачу,
  conventional commits).

## 4. Шаг 2 — Семантическая разметка `with_rules/index.html`

### 4.1 Промпт (RTCF)

```text
R: Ты — фронтенд-разработчик проекта (HTML5, семантика).
   Прочитай hw_ai_rules.md и rules.md (R2) и строго им следуй.
T: Создай index.html со всеми секциями: шапка/навигация, hero, услуги/прайс,
   галерея, о мастере, запись (форма), контакты, футер.
C: Классы БЭМ kebab-case (R7); семантика и a11y (осмысленные alt, aria-live
   у статуса формы, role=dialog/aria-modal у лайтбокса, progressive enhancement) — R5.
   Контейнеры-заглушки под JS: #services-list, #gallery-grid, #lightbox,
   форма #booking-form (novalidate). Подключение css/main.css, css/components.css,
   js/main.js type=module (R12). Структура каталога — строго по hw_ai_rules п.3.1.
F: Полный готовый index.html без плейсхолдеров; комментарии «почему» (R8).
   Коммит на ветке feature/site-with-rules (R14).
```

### 4.2 Результат

- Создан `with_rules/index.html` со всеми секциями; семантика `<header>/<nav>/<main>/<section>/<address>/<footer>`.
- Доступность: осмысленные `alt`, `aria-live="polite"` у статуса формы,
  `role="dialog"`/`aria-modal` у лайтбокса, доступность с клавиатуры (R5).
- Прогрессивное улучшение: контейнеры услуг/галереи пустые в разметке — наполняются
  JS; без JS страница остаётся читаемой (R5).
- Добавлены placeholder-изображения (SVG) в `with_rules/assets/images/`
  (hero, master, work-1..6) — ссылки корректны, страница не выдаёт ошибок.

**Commit:** `feat(html): разметка главной страницы со всеми секциями (вариант с правилами)`.

## 5. Шаг 3 — Стилизация `with_rules/css/`

### 5.1 Промпт (RTCF)

```text
R: Ты — CSS-разработчик проекта. Прочитай hw_ai_rules.md и rules.md (R2).
T: Создай css/main.css (переменные :root, базовые стили, секции)
   и css/components.css (переиспользуемые компоненты: кнопки, карточки,
   галерея/лайтбокс, форма записи).
C: CSS-переменные для палитры и отступов (R9 / hw_ai_rules п.4.3);
   БЭМ-классы; медиазапросы рядом с блоком; без !important (или причина
   в комментарии); контраст WCAG AA (R5); именование kebab-case (R7).
   Повторно используемые части — в components.css (R13).
F: Два готовых файла с указанием, где что живёт.
```

### 5.2 Результат

- `with_rules/css/main.css` — переменные `:root`, базовые стили, секции,
  медиазапросы рядом с блоками (R9).
- `with_rules/css/components.css` — кнопки `.button--*`, карточки услуг,
  галерея/лайтбокс, форма записи (R13: вынос повторно используемых частей).
- В `components.css` осознанно переопределён `.lightbox[hidden]` — причина указана
  комментарием (R9: без `!important`, с пояснением селектором).

**Commit:** `feat(css): стилизация страницы с переменными и переиспользуемыми компонентами (вариант с правилами)`.

## 6. Шаг 4 — Модульная JS-логика `with_rules/js/`

### 6.1 Промпт (RTCF)

```text
R: Ты — JS-разработчик проекта (vanilla, ES-модули). Прочитай оба файла правил (R2).
T: Создай js/utils.js (хелперы) и модули по предметным областям (R13):
   services.js (данные + рендер карточек + наполнение select),
   gallery.js (лайтбокс, закрытие Esc/клик по фону),
   booking.js (чистая validateBooking + initBooking),
   contacts.js (год в футере), точку входа js/main.js (R12).
C: const по умолчанию, let при переприсваивании, строгие проверки === (R9);
   функции «один смысл» до ~40 строк (R9); guard-check на отсутствие контейнера
   (progressive enhancement R5); обработка ошибок с понятными сообщениями (R9);
   без секретов в коде (R10); комментарии «почему» (R8); рус/англ единообразно.
F: Полные файлы, перечень функций; commit на ветке feature/site-with-rules.
```

### 6.2 Результат

- `with_rules/js/utils.js` — `getElementById`, `formatPrice`, `SERVICE_CATEGORIES`, `isNonEmptyString`.
- `with_rules/js/modules/services.js` — массив `SERVICES` (7 услуг), `renderServices()`,
  `populateBookingSelect()`.
- `with_rules/js/modules/gallery.js` — массив `WORKS` (6 работ), `initGallery()` с лайтбоксом,
  закрытием по Esc/клику по фону; открытие/закрытие с клавиатуры (R5).
- `with_rules/js/modules/booking.js` — `validateBooking()` (чистая функция), `initBooking()`.
- `with_rules/js/modules/contacts.js` — `initContacts()` (текущий год в футере).
- `with_rules/js/main.js` — точка входа `initApp()`.

Все модули безопасно завершаются при отсутствии контейнера (progressive enhancement R5).
Синтаксис проверен: `node --check` по всем 6 файлам — без ошибок (самопроверка R3).

**Commit:** `feat(js): модули услуг, галереи, записи и контактов (вариант с правилами)`.


## 7. Шаг 5 — Тесты, проверка, документация

### 7.1 Промпт (RTCF)

```text
R: Ты — QA-инженер + code-reviewer проекта. Прочитай оба файла правил (R2).
T: Проверь валидность HTML/CSS/JS, отсутствие синтаксических ошибок;
   напиши юнит-тесты для validateBooking без внешнего фреймворка.
C: Правила hw_ai_rules.md п.5.3 (проверки перед сдачей) + self-check R3
   (не ломать существующие конвенции, без лишнего кода).
F: Отчёт о проверке, покрытые/непокрытые кейсы, создание документации:
   cot_progress_with_rules.md и сравнения comparison_with_vs_without_rules.md.
```

### 7.2 Результат проверок

- **Синтаксис JS:** `node --check` для всех 6 файлов — без ошибок.
- **Юнит-тесты:** `node --test with_rules/tests/booking.test.js` — **8/8 прошли**.
  Покрытые кейсы: валидная форма, пустое имя, пустой/некорректный телефон,
  телефон без разделителей, невыбранная услуга, пустая дата, множественные ошибки.
- **Файлы/структура:** `with_rules/` соответствует `hw_ai_rules.md` п. 3.1 и `rules.md` R12.
- **Самопроверка R3:** запущены `node --check` и `node --test` перед коммитами;
  лишний код не генерировался.

**Commit:** `test(booking): юнит-тесты валидации формы записи (вариант с правилами)`.

### 7.3 Непокрытые сценарии (информация)

- Валидация **даты «не в прошлом»** — намеренно не реализована (в эталоне её тоже нет,
  чтобы сохранить сравнимость); `date` проверяется только на непустоту.
- Обработка **сетевых/серверных** ошибок отправки формы — сайт статический, отправка
  имитируется клиентским модулем (R4/R5).

## 8. Итоговые выводы о применении CoT (вариант «с правилами»)

1. **Декомпозиция снизила риск ошибок.** Разделение на HTML → CSS → JS → тесты
   позволило проверять и коммитить каждый слой отдельно (8 коммитов на этой ветке).
2. **Чистые функции облегчают тестирование.** Выделение `validateBooking()` без
   DOM-зависимостей позволило покрыть её юнит-тестами в Node без браузера.
3. **Промпт по RTCF даёт предсказуемый результат.** Роль/задача/контекст/формат,
   согласованные с правилами R2–R14, устраняют неоднозначность ожиданий.
4. **Progressive enhancement и a11y заложены в контекст промптов (R5)** — сайт
   работоспособен без JS и доступен с клавиатуры.
5. **Наличие правил сделало исполнение строже детерминированным** (R12–R14):
   чёткая структура файлов, вынос компонентов в `components.css`, ветка
   `feature/site-with-rules` и conventional commits. Подробнее — в файле сравнения.
