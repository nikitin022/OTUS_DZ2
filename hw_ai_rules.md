# HW_AI_RULES — свод правил разработки

> Файл-«памятка» для ИИ-агентов и участников команды. Содержит краткое описание проекта,
> стек и единые требования к стилю кода, архитектуре и стандартам разработки.
> При выполнении любых задач (генерация кода, рефакторинг, код-ревью, написание тестов)
> следуйте этим правилам. При конфликте с общими подсказками инструментов приоритет за этим файлом.

---

## 1. О проекте

**Название:** «Сайт услуг парикмахера и массажиста»
**Назначение:** публичный сайт-визитка для мастера, предоставляющего услуги
парикмахерского искусства и массажа. Позволяет пользователю:

- ознакомиться с перечнем и описанием услуг;
- увидеть прайс/стоимость работ;
- посмотреть примеры работ (галерея) и информацию о мастере;
- связаться с мастером (запись на услугу, контакты, форма обратной связи);
- получить информацию о локации и режиме работы.

Проект — учебный, относится к **ДЗ2** курса OTUS «ИИ-агенты».

## 2. Технологический стек

| Слой | Технология |
|------|------------|
| Клиентская логика | **JavaScript (ES2020+)** |
| Разметка | **HTML5** (семантическая разметка) |
| Стилизация | **CSS3** (минимальный фреймворк/препроцессор по согласованию) |
| Инструменты | NPM/Yarn, Git |
| Разрешённые библиотеки | лёгкие vanilla-решения; фреймворки (**Vue/React**) — только по отдельному решению команды |

### Принципы стека
- **Статический сайт без жёсткой зависимости от сервера** (может работать из `file://` или любого хостинга статики).
- Внешние зависимости (CDN-библиотеки, иконки, шрифты) — минимальны и явно документированы.
- Всё, что не является обязательной зависимостью, реализуется на нативном JS/CSS.

## 3. Архитектура и структура проекта

### 3.1 Требуемая структура каталогов
```
.
├── index.html              # Главная страница
├── css/
│   ├── main.css            # Основные стили и переменные
│   └── components.css      # Стили повторно используемых компонентов
├── js/
│   ├── main.js             # Точка входа, инициализация
│   ├── modules/            # Модули по ответственности
│   │   ├── services.js     # Логика услуг/прайса
│   │   ├── gallery.js      # Галерея работ
│   │   ├── booking.js      # Форма записи
│   │   └── contacts.js     # Контакты/карта
│   └── utils.js            # Утилиты/хелперы
├── assets/
│   ├── images/             # Изображения (оптимизированные)
│   └── fonts/              # Локальные шрифты (если есть)
├── hw_ai_rules.md          # Настоящий файл
└── README.md               # Описание и инструкция запуска
```

### 3.2 Принципы
- **Разделение ответственности:** разметка, стиль и логика отделены (не путать).
- **Модульность:** функционал, разделённый на независимые модули в `js/modules/`.
- **Повторное использование:** общие компоненты (кнопки, карточки, модалки) выносятся в переиспользуемые части стилей.
- **Прогрессивное улучшение:** сайт должен оставаться читаемым и рабочим без JS; JS-логика — улучшение, а не основа.
- **Доступность (a11y):** осмысленные `alt`, семантические теги, рабочая навигация с клавиатуры, контраст соответствующий WCAG AA.

## 4. Стандарты и стиль кода

### 4.1 Общие
- Кодировка UTF-8, отступы — **2 пробела**, завершение строки LF.
- Стиль именования:
  - `HTML`/`CSS`: `kebab-case` (например `.main-nav`, `button-hero`);
  - `JS`: `camelCase` для переменных/функций, `PascalCase` для классов/конструкторов, `CONSTANTS_IN_UPPER_SNAKE_CASE`.
- Комментарии — на русском или английском (единоразовый выбор для файла). Кратко объясняют «почему», а не дублируют код.
- Без транслита и без мешанины латиницы/кириллицы в одном файле.

### 4.2 JavaScript
- ES модули (`import`/`export`).
- `'use strict'`-морально; использование `const` по умолчанию, `let` когда нужно переприсваивание, `var` — запрещено.
- Строгая проверка открытия через `===`/`!==`.
- Обработка ошибок: `try/catch` или отлов в промисах; пользователю показываются понятные сообщения.
- Продуманная абстракция: функции «одна — один смысл», длина в пределах ~40 строк.
- Даже приватные, но значимые данные не зашивают прямо в код (ключи API — в переменных окружения/конфиге, не в репозиторий).

### 4.3 CSS
- Использование CSS-переменных (`:root`) для палитры и отступов.
- Порядок медиазапросов — рядом с блоком, к которому относятся.
- Классы БЭМ-подобные: `block`, `block__elem`, `block--modifier`.
- Избегать `!important` (комментарий и причина, если неизбежно).

## 5. Стандарты разработки и процесса

### 5.1 Коммиты (Conventional Commits)
`<type>(<scope>): <описание>` — например:
- `feat(booking): добавить форму записи`
- `fix(gallery): исправить перелистывание на мобильных`
- `refactor(services): вынести прайс в данные`
- `docs: обновить hw_ai_rules.md`

### 5.2 Ветвление
- Ветка на задачу: `feature/название`, `fix/описание`. В слитие в `main` после ревью.

### 5.3 Проверка перед сдачей
1. Валидность HTML/CSS/JS (линтер и ручная проверка).
2. Сайт открывается и работает («смотрится» набегом в браузере).
3. Проверено адаптацию (mobile/desktop).
4. Проверена доступность базовых элементов (клавиатура, контраст).
5. Имена и формулировки на русском без опечаток.

### 5.4 Работа ИИ-агента над этим проектом
1. Сначала прочитать `hw_ai_rules.md` и соответствовать ему.
2. Прежде чем менять код — осмотреть существующую структуру и не ломать конвенций.
3. Перед коммитом — прогон линтера/проверка синтаксиса и минимальная самопроверка изменяемого функционала.
4. Не генерировать лишнего кода; каждая правка должна быть обоснована запросом.
