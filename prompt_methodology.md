# PROMPT_METHODOLOGY — методология промптов (RTCF)

> Набор шаблонов промптов для работы ИИ-агента над проектом
> «Сайт услуг парикмахера и массажиста» (ДЗ2, OTUS «ИИ-агенты»).
> Каждый промпт строится по структуре **RTCF**:
> **R**ole (Роль) → **T**ask (Задача) → **C**ontext (Контекст) → **F**ormat (Формат).
>
> Шаблоны согласованы с правилами проекта (`hw_ai_rules.md`, `rules.md`):
> стек HTML5/CSS3/JS (ES2020+, vanilla), статический сайт, БЭМ-подобные классы,
> `kebab-case`/`camelCase`/`PascalCase`, Conventional Commits.

---

## 0. Универсальная последовательность (цепочка промптов)

Цепочка применения любого шаблона для **полного цикла разработки**:

1. **RTCF-промпт** (по выбранному сценарию ниже) → получаешь результат.
2. **Проверка на правила** — сверить результат с `hw_ai_rules.md` / `rules.md`
   (стиль, структура, запреты).
3. **Самопроверка/ревью** — прогон линтера, проверка синтаксиса и функционала.
4. **Коммит (conventional).**
5. **Финализация** — краткое резюме изменений: что сделано и как протестировано.

## 1. Генерация компонента/функции по описанию

**R — Роль:**
Ты — фронтенд-разработчик проекта «Сайт услуг парикмахера и массажиста».
Создаёшь новый компонент/функцию по описанию, строго следуя правилам проекта.

**T — Задача:**
Создай описанный компонент/функцию с учётом стека (HTML/CSS/vanilla JS),
архитектуры (модули по ответственности) и стиля кода (2 пробела, kebab-/camel-,
комментарии «почему»).

**C — Context:**
Дай: назначение компонента; место размещения (файл); откуда приходят данные
и куда они должны выводиться; связанные существующие модули/файлы; требования
к доступности (alt, семантика, клавиатура) и адаптивности.

**F — Format:**
Верни готовый код с точным указанием файла для размещения, без плейсхолдеров;
добавь комментарии в стиле проекта и краткое описание, как встроить компонент
в страницу (`index.html`/`main.js`).

### Пример использования
```text
R: Ты — фронтенд-разработчик проекта «Сайт услуг мастера», vanilla JS.
T: Создай модуль «галерея работ»: сетка карточек, лайтбокс по клику.
C: Проект статический (file://), ES-модули. Расположить в js/modules/gallery.js,
   стили в css/components.css (БЭМ: gallery, gallery__card, gallery--open).
   Данные — массив {src, alt, caption}. Учитывай a11y: альтернативы и клавиши.
F: Файл js/modules/gallery.js (export функции), блок CSS-классов, минипример,
   инструкция подключения-инициализации из js/main.js.
```

## 2. Рефакторинг кода с улучшением

**R — Роль:**
Ты — senior-разработчик проекта, выполняющий рефакторинг существующего кода.

**T — Задача:**
Проведи рефакторинг указанного фрагмента: улучши читаемость, структуру и
производительность, **не меняя внешнего поведения**.

**C — Context:**
Дай полный текущий код (или путь файла) и его назначение; укажи болезненные
места (дублирование, длинные функции, вложенность, проблемы a11y/перформанс);
способ проверки результата (тесты/ручная проверка).

**F — Format:**
Верни «до/после» (diff или оба фрагмента); перечисли изменения с обоснованием;
новый код оформи в блоке с указанием файла; подтверди, что поведение сохранено,
и предложи коммит по conventional commits (`refactor: ...`).

### Пример использования
```
R: Ты — senior-разработчик проекта, соблюдай разделение ответственности.
T: Отрефактори js/modules/booking.js: вынеси валидацию формы, убери дублирование.
C: Код прилагается. Цель — валидация и отправка формы. Проблемы: 40-строчная
   функция submitHandler, повторяющаяся обработка ошибок инпутов.
   Проверка — вручную открыть index.html, форма работает без ошибок.
F: «До/после» с обоснованием изменений; подтверди сохранение поведения;
   предложи коммит refactor(booking): упростить валидацию формы.
```

## 3. Написание тестов для существующего кода

**R — Роль:**
Ты — QA-инженер, пишущий тесты для JavaScript-логики проекта.

**T — Задача:**
Напиши тесты (или тест-план) для указанного модуля, покрыв основные и
граничные сценарии.

**C — Context:**
Дай код/модуль и его публичный интерфейс (экспортируемые функции, ожидаемые
входы/выходы); укажи тест-фреймворк (или отметь, что нужен внешний), выдели
важные edge-кейсы (пустые данные, неверный формат, недоступность сети).

**F — Format:**
Верни структуру: список кейсов назначения → код тестов в стиле проекта;
отдельно команды запуска; перечисли покрытые и непокрытые сценарии; при нужде
— коммит `test(scope): ...`.

### Пример использования
```
R: Ты — QA-инженер vanilla JS-проекта.
T: Напиши тесты для валидации формы js/modules/booking.js (validateBooking).
C: Функция получает объект {name, phone, service, date} и возвращает
   {valid, errors}. Кейсы: пустое имя, неверный телефон, пустое date,
   корректная форма. Фреймворк отсутствует — использовать простой assert.
F: Файл tests/booking.test.js, перечень кейсов и покрытие, команда запуска
   (node tests/booking.test.js), коммит test(booking): ...
```

## 4. Исправление ошибок и багов

**R — Роль:**
Ты — разработчик-debugger: находишь корень ошибки и применяешь исправление.

**T — Задача:**
Найди причину бага, предложи и примени исправление, убедись, что баг исчез
и не появились регрессии.

**C — Context:**
Опиши симптом (фактическое поведение) и ожидаемое; приложи код/файлы, ошибки
консоли и шаги воспроизведения; укажи, есть ли тесты для проверки.

**F — Format:**
Ответь в порядке: 1) диагноз (причина), 2) правка с diff и указанием файла,
3) способ проверки, 4) коммит `fix(scope): ...`, 5) рекомендация против
повторного возникновения.

### Пример использования
```
R: Ты — debugger JS-проекта.
T: Исправь ошибку при рендере цен в js/modules/services.js.
C: Симптом: при открытии блока «Услуги» консоль:
   `Cannot read properties of undefined (reading 'length')` на строке 12.
   Ожидание: список отображается, ошибок нет. Условия: массив услуг может
   приходить пустым. Шаги: открыть index.html → раздел «Услуги». Тестов нет.
F: 1) причина — нет guard-check на пустые данные; 2) дифф с проверкой
   Array.isArray(data); 3) проверка в браузере; 4) fix(services): защита от пустых данных;
   5) совет — нормализовать данные при загрузке.
```

## 5. Декомпозиция сложной задачи на подзадачи

**R — Роль:**
Ты — технический архитектор / тимлид проекта.

**T — Задача:**
Декомпозируй общую задачу на независимые подзадачи с понятными критериями
готовности, порядком и зависимостями.

**C — Context:**
Дай формулировку общей задачи/эпика, цель и ограничения (стек, структура
каталогов); укажи существующие модули и файлы проекта.

**F — Format:**
Верни упорядоченный план: подзадача → файлы/модули → приёмные критерии →
приоритет и зависимости; для каждой подзадачи укажи тип conventional commits.
Заверши обобщённой последовательностью выполнения.

### Пример использования
```
R: Ты — тимлид проекта «Сайт услуг мастера».
T: Декомпозируй задачу «Реализовать страницу услуги с прайсом и записью».
C: Проект использует js/modules/services.js, js/modules/booking.js, index.html;
   стили — css/main.css. Ограничения: статический сайт, vanilla JS, БЭМ.
F: План подзадач:
   1) services — разметка + данные прайса (js/modules/services.js) — accept:
      отображаются услуги и цены; commit feat(services): ...
   2) booking — форма и валидация (js/modules/booking.js) — accept: валидная
      отправка; commit feat(booking): ...
   3) стили (css/components.css) — accept: адаптив на мобайл; commit style(...): ...
   Зависимости: 2 зависит от 1; 3 параллельна 1–2. Приоритет: 1 → 3 → 2.
```
