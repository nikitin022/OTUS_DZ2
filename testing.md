# TESTING — тестирование влияния правил на вывод агента (ДО и ПОСЛЕ)

> Документ по формату сдачи ДЗ2: фиксирует **сырые ответы агента** на одну и ту же
> задачу **до** применения файла правил и **после** применения правил, а также
> краткий вывод. Дополнительно — расширенное сравнение двух полных циклов
> разработки сайта-визитки.

## 1. Контролируемый эксперимент на изолированной задаче

Чтобы оценить влияние правил без «шума» большой задачи, взята небольшая изолированная
задача — **функция валидации формы записи** `validateBooking(data)`. Оба прогона
получают одну и ту же формулировку; единственное отличие — передача агенту файла правил.

### 1.1 Промпт (одинаковый для обоих прогонов)

```text
R: Ты — фронтенд-разработчик, пишущий на vanilla JS (ES2020+).
T: Напиши чистую функцию validateBooking(data), которая валидирует данные формы
   записи: name — непустая строка; phone — непустой и в формате +7 XXX XXX-XX-XX
   (пробелы/дефисы необязательны); service — непустая строка; date — непустая строка.
   Функция не должна зависеть от DOM.
C: Данные приходят объектом { name, phone, service, date }.
   Некорректный ввод должен помечаться понятным сообщением пользователю.
F: Верни полный код функции на ES2020+ (export), без плейсхолдеров.
```

### 1.2 Прогон «до правил» — сырой ответ агента (без файла правил)

Ниже приведён **сырой ответ агента** без каких-либо файлов правил
(без `hw_ai_rules.md` и без `rules.md`), без последующих правок:

```js
// booking.js — модуль формы записи

function validateBooking(data) {
  var errors = {};

  if (data.name.trim() == '') {
    errors['name'] = 'Укажите имя';
  }

  if (data.phone == '') {
    errors['phone'] = 'Укажите телефон';
  } else {
    // Проверяем, что номер содержит 11 цифр
    var digits = data.phone.replace(/\D/g, '');
    if (digits.length != 11) {
      errors['phone'] = 'Телефон некорректный';
    }
  }

  if (data.service == '') {
    errors['service'] = 'Выберите услугу';
  }

  if (data.date == '') {
    errors['date'] = 'Выберите дату';
  }

  var valid = false;
  if (Object.keys(errors).length == 0) {
    valid = true;
  }

  return { valid: valid, errors: errors };
}
```

Что видно в сыром ответе:

- `var` вместо `const`, нестрогие сравнения `==` вместо `===`;
- `data.name.trim()` без защиты — исключение, если `data` или поле отсутствуют
  (например, при вызове `validateBooking({})`);
- проверка телефона «по числу цифр», а не по строгому формату `+7 XXX XXX-XX-XX`
  (телефон `8 900 000-00-00` пройдёт, хотя по ТЗ нужен `+7`);
- пробельные значения не отсекаются (`data.phone == ''` не поймает `'   '`);
- избыточная переменная `valid` и комментарий-пересказ кода.

### 1.3 Прогон «после правил» — сырой ответ агента (с правилами)

Тот же промпт, но перед ответом агенту переданы `hw_ai_rules.md` и `rules.md` (R1–R14).
**Сырой ответ агента** (без последующих правок):

```js
// utils.js — хелперы (R9: const, строгие проверки ===)
const isNonEmptyString = (value) => typeof value === 'string' && value.trim() !== '';

// booking.js — модуль формы записи: валидация и понятные сообщения пользователю (R9, R13).
// Телефон в формате +7 XXX XXX-XX-XX (пробелы/дефисы необязательны)
const PHONE_PATTERN = /^\+7[\s-]?\d{3}[\s-]?\d{3}[\s-]?\d{2}[\s-]?\d{2}$/;

/**
 * Валидирует данные формы. Чистая функция без DOM-зависимостей — легко тестировать.
 * @param {{ name: string, phone: string, service: string, date: string }} data
 * @returns {{ valid: boolean, errors: Record<string, string> }}
 */
export function validateBooking(data) {
  const errors = {};

  if (!isNonEmptyString(data.name)) {
    errors.name = 'Укажите ваше имя.';
  }

  if (!isNonEmptyString(data.phone)) {
    errors.phone = 'Укажите номер телефона.';
  } else if (!PHONE_PATTERN.test(data.phone.trim())) {
    errors.phone = 'Телефон должен быть в формате +7 XXX XXX-XX-XX.';
  }

  if (!isNonEmptyString(data.service)) {
    errors.service = 'Выберите услугу из списка.';
  }

  if (!isNonEmptyString(data.date)) {
    errors.date = 'Выберите желаемую дату.';
  }

  return { valid: Object.keys(errors).length === 0, errors };
}
```

Этот вариант соответствует правилам: `const`/`===` (R9), guard-check через хелпер
`isNonEmptyString` (пустые и пробельные значения обрабатываются без исключений),
строгий формат телефона, комментарии «почему» (R8), чистая функция готова
к юнит-тестам (R13).

### 1.4 Краткий вывод по эксперименту

- **Функциональность** сопоставима: обе версии возвращают `{ valid, errors }` и
  отлавливают базовые ошибки формы.
- **Устойчивость к граничным случаям** выше с правилами: версия «до правил» падает
  с исключением на пустом объекте (`data.name.trim()`), версия с правилами — нет
  (защита через `isNonEmptyString`).
- **Соответствие ТЗ** точнее с правилами: строгий формат `+7 ...` вместо «11 цифр».
- **Стиль и поддерживаемость** выше с правилами: `const`/`===`, комментарии «почему»,
  чистая функция без избыточных переменных.
- **Итог:** файл правил не меняет суть решения, но повышает предсказуемость,
  защищённость от невалидного ввода и соответствие принятым стандартам кода.

## 2. Расширенное сравнение на крупной задаче (сайт)

Помимо изолированной задачи, техника **Chain-of-Thought (CoT)** применена к полному
циклу разработки сайта «Сайт услуг парикмахера и массажиста» в двух вариантах:

- **Вариант A (базовый)** — каталог `without_rules/`, документация
  `cot_progress_without_rules.md`: использовались базовые правила `hw_ai_rules.md`;
- **Вариант B (с правилами)** — каталог `with_rules/`, документация
  `cot_progress_with_rules.md`: применялись `hw_ai_rules.md` **и** детализированные
  `rules.md` (R1–R14).

> Уточнение: здесь «базовый» означает «без детализированного файла правил
> `rules.md`». Чистый прогон **совсем без правил** приведён в разделе 1
> на изолированной задаче.

### 2.1 Методология сравнения

Оба цикла устроены одинаково, чтобы изолировать влияние `rules.md`:

| Параметр | Значение в обоих вариантах |
|----------|---------------------------|
| Задача | Один и тот же сайт-визитка мастера (все разделы) |
| Техника | CoT, декомпозиция на те же 5 шагов (HTML → CSS → JS → тесты → документация) |
| Методология промптов | RTCF (Role → Task → Context → Format) |
| Схемы данных | `{id,name,category,price,duration,alt}` и `{src,alt,caption}` |
| Стек | Статический сайт `file://`, HTML5/CSS3/vanilla JS (ES-модули) |
| Единственное отличие | Наличие файла `rules.md` (R1–R14) |

**Критерии сравнения:** структура файлов (R12/п.3.1), вынос компонентов (R13),
стиль кода (R8–R9), a11y и progressive enhancement (R5), отсутствие секретов (R10),
контроль и отсутствие лишнего кода (R3), conventional commits и ветвление (R14),
тесты и найденные в ходе CoT дефекты.

### 2.3 Ключевое различие: дефект лайтбокса

- **Вариант A:** в ходе Шага 4 выявлен баг — кнопка закрытия лайтбокса искалась
  через `grid.querySelector`, тогда как она находится в `lightbox`. Исправлен до этапа
  проверок (`fix`).
- **Вариант B:** благодаря требованию R3 («осмотри текущую структуру, не ломай
  конвенции») и явному упоминанию в контексте промпта правильная область поиска
  (`lightbox.querySelector`) заложена сразу, **дефект не возник**. Как следствие —
  в варианте B **нет отдельного `fix`-коммита**, что упрощает историю.

### 2.4 Выводы: где правила реально повлияли

1. **Процесс стал детерминированнее.** R2 («сначала прочитай правила») и R3
   («осмотри структуру, без лишнего кода») снижают вероятность «творческих» отступлений
   и уменьшают число дефектов, найденных на поздних шагах.
2. **Структура и компоненты предписаны явно** (R12–R13), поэтому решение по разбиению
   файлов не зависело от догадок агента — оба варианта совпали, но «с правилами»
   быстрее и с меньшим числом итераций.
3. **Стиль и безопасность зафиксированы нормативами** (R8–R10): единообразные
   комментарии, `const`/`===`, отсутствие секретов — применялись осознанно.
4. **История коммитов чище** в варианте с правилами (отсутствует поздний `fix`).

### 2.5 Выводы: где разницы нет

1. **Функциональность и архитектура** одинаковы — задача, декомпозиция CoT и схемы
   данных совпадают, поэтому итоговый сайт и тесты эквивалентны (8/8 в обоих).
2. **Качество a11y и адаптива** на одинаковом уровне — требования уже заложены
   в `hw_ai_rules.md` (общий для обоих).
3. **Объём кода** практически не различается — правила не добавляют «лишнего кода»
   (что соответствует духу R3).

## 3. Итоговый вывод

Применение файла правил (раздел 1 — на изолированной задаче, раздел 2 — на сайте)
не меняет функциональность, но делает процесс разработки более **предсказуемым,
аккуратным и менее подверженным поздним дефектам** — прежде всего за счёт правил R2–R3
(чтение правил перед кодом и грамотная самопроверка), R12–R13 (структура и компоненты)
и R14 (conventional commits и ветвление).
